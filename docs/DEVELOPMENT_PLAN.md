# 知库 AI（KnowBase AI）V1.0 开发计划书 · v2

> **v2 修订说明**：v1 的问题是把"工程完整性"排在了"技术可行性验证"之前，导致文档链路要等到第 4 周才第一次真正跑通。v2 改为**纵向切片优先**：第 1–2 周就用一个 TXT 打通"上传 → 解析 → 向量化 → 检索 → 生成 → 引用"的全链路，之后再用 8 周补权限、可靠性、体验和交付。
> v1 的阶段划分、任务编号、范围冻结机制保留；时间线、里程碑、数据库数量、状态机、启动方式、测试节奏重写。修订对照见 §14。

**目标：** 10 周交付一个可演示的系统，另留 2 周缓冲吸收延期。主线是一条**有权限边界、有失败恢复、引用可追溯**的端到端链路。

**架构：** Vue 3 + Spring Boot 模块化单体（业务与权限的唯一权威源）+ FastAPI（只做 AI 计算，无权限决策权）+ MySQL / Redis / Qdrant / 本地文件存储。

**规格来源：** `项目书.md`

---

## 1. 这份计划怎么用

1. **按 Stage 顺序，不跳阶段。** Stage N 出口不通过，不进 N+1。
2. **任务编号 `T<阶段>.<序号>`**，做完勾选；做不完登记进 `docs/KNOWN_ISSUES.md`，不静默跳过。
3. **每个 Stage 结束必须有一个能当场演示的动作。**
4. **测试与实现同阶段**，不允许堆到最后（见 §10）。
5. 第 11–12 周是**缓冲，不排任务**。如果第 10 周末已交付，这两周用来补 P2 和打磨；如果延期，用它吸收。**不要把缓冲提前花掉。**

## 2. 范围与优先级

### 2.1 三级优先级（时间不够时的裁剪顺序）

| 级别 | 内容 | 裁剪规则 |
|---|---|---|
| **P0 核心闭环** | 登录、知识库权限、文档上传解析、向量检索、RAG 问答、真实引用、Docker 部署 | **绝不裁剪。** 任何一项缺失，项目不成立 |
| **P1 工程质量** | 任务失败恢复、模型配置、审计日志、关键自动化测试、SSE 流式 | 时间紧时降级实现（如流式改为一次性返回），但不删 |
| **P2 加分项** | 完整评估报告、复杂监控、备份恢复自动化、视觉优化、多知识库问答 | 时间不够**第一个砍** |

> 判断标准：一个功能如果被砍掉后**演示仍然成立且答辩讲得通**，它就是 P2。

### 2.2 页面（7 个）

| 编号 | 页面 | 优先级 |
|---|---|---|
| P1 | 登录 | P0 |
| P2 | 工作台（真实统计，不造假数据） | P2 |
| P3 | 知识库列表 | P0 |
| P4 | 知识库详情（文档 / 成员 两 Tab） | P0 |
| P5 | 文档详情（状态 + 分片预览） | P0 |
| P6 | 智能问答（对话 + 引用） | P0 |
| P7 | 系统设置（用户 / 模型 / 审计 三 Tab，仅管理员） | P1 |

### 2.3 明确不做（写进 README 与代码注释）

文档版本历史、检索调试页、RAG 评估平台化、站内通知/邮件、消息队列、OCR、混合检索、Reranker、多租户、计费、SSO、移动端、i18n、微服务、K8s、CI/CD 流水线。

### 2.4 与项目书的四处差异（已确认）

| 项目书 | v2 | 理由 |
|---|---|---|
| 16 页面 | 7 页面（Tab 合并） | 页面数是最大时间黑洞 |
| 第 6 周末可演示 | 第 6 周末完整演示，第 2 周末已有最小闭环 | 纵向切片让风险提前暴露 |
| Redis 定位模糊 | 承担**登录失败计数 + 问答限流 + token 版本缓存** | 给它真实职责 |
| Ollama 作为备份模型 | **可选加分项，不是必须交付** | 4C8G 不能保证任意本地模型可跑；不写"自动容灾" |

## 3. 前置决策（含本轮新增/修正）

| # | 决策 | 值 |
|---|---|---|
| D1 | 部署目标 | 单机 Docker Compose |
| D2 | 资源下限 | 4C8G / 30G 磁盘 |
| D3 | 文件存储 | 宿主目录挂载 `./data/uploads`，不引入 MinIO |
| D4 | 任务调度 | `@Scheduled` 轮询 + **条件 UPDATE 原子认领**，不引入 MQ |
| D5 | 流式输出 | SSE |
| D6 | 鉴权 | JWT + **`token_version` 失效机制**（见 D9） |
| D7 | 依赖版本 | T0.6 锁定到 `docs/STACK.md` |
| D8 | 模型 | **至少一家外部 OpenAI 兼容服务必须跑通**；Ollama 可选 |
| D9 | 登出/改密/禁用失效 | JWT 携带 `uid + ver`；`sys_user.token_version` 自增即失效。不引入黑名单 |
| D10 | 双启动模式 | `dev`：MySQL/Redis/Qdrant 在容器，Java/Python/前端本地热重载。`demo`：全部容器 + Nginx。**两种模式各有独立脚本和验收步骤**（见 §9.4） |
| D11 | 主密钥 | `APP_MASTER_KEY`（32 字节 base64）放 `.env`，不进版本库；`ai_model_config.api_key_cipher` 用它做 AES-GCM |
| D12 | 检索授权范围 | **由 Java 计算后传入 Python**，Python 不接受客户端传入的 kb 范围 |

**已知的技术债（故意留到 Stage 2）**：无权限隔离、无任务队列、无重试、无去重、无格式校验、无删除。

### 7.2 每张表必须声明的六项（统一约束）

**建表前每张表都要在 `DATABASE.md` 里写全这六项，缺一项不进入编码：**

1. **主键策略** — 统一 `BIGINT AUTO_INCREMENT`（`sys_*` 用 `INT`）。不用 UUID 做主键（索引膨胀），UUID 只用于文件存储名。
2. **唯一约束** — 见下表。
3. **查询索引** — 每个列表页的筛选/排序组合各建一个复合索引，最左前缀匹配。
4. **外键策略** — 见 7.3。
5. **时间戳** — 所有表含 `created_at`；可变表含 `updated_at`。统一 `DATETIME(3)`，由应用层写入，不用数据库默认值（便于测试可控）。
6. **删除策略** — 见 7.3。

### 7.3 外键与删除策略（新）

| 动作 | 策略 | 理由 |
|---|---|---|
| 删除用户 | **禁用**（`status=DISABLED`），不物理删 | 审计日志要指向真实主体 |
| 删除知识库 | 默认**归档**（`ARCHIVED`）；仅当无文档且无会话引用时允许物理删 | 避免级联雪崩 |
| 删除文档 | **软删除**：`status: ACTIVE → DELETING → DELETED`，物理行保留 | 需保留审计与重试依据；文件与向量异步清理 |
| 删除会话 | **物理删除**，级联删 `ai_message` → `ai_message_citation` | 无审计价值，且用户预期"删了就没了" |
| 删除分片 | 随文档清理，物理删 | 分片无独立生命周期 |

**外键**：核心关联（`kb_member.kb_id/user_id`、`kb_document.kb_id`、`kb_document_chunk.doc_id`、`ai_message.conversation_id`、`ai_message_citation.message_id/chunk_id`）使用**真实外键 + `ON DELETE RESTRICT`**。不用 `CASCADE`——级联删除不可控且与软删除策略冲突，统一由应用层按上表顺序处理。

## 8. 状态机与并发控制（本轮重点补充）

### 8.1 状态定义

```
kb_document.status
  PENDING ──► PROCESSING ──► ACTIVE
     ▲            │             │
     │            ▼             ▼
     └──── FAILED │         DELETING ──► DELETED
                  └──► FAILED        └──► DELETE_FAILED (可重试)

kb_ingestion_task.status
  QUEUED ──► RUNNING ──► SUCCESS
     ▲          │
     │          ├──► FAILED (attempt < max)
     └──────────┘ (人工重试)
             └──► DEAD (attempt >= max，需人工介入)
```

### 8.2 原子认领（MySQL 落地方案）

MySQL 没有 PostgreSQL 的部分唯一索引，不能靠 `UNIQUE(doc_id) WHERE status IN (...)` 约束防重。**改用条件 UPDATE + 行锁**：

```sql
-- 1) 取候选（MySQL 8.0+ 支持 SKIP LOCKED，避免多实例互等）
SELECT id FROM kb_ingestion_task
WHERE status = 'QUEUED'
ORDER BY created_at
LIMIT 5
FOR UPDATE SKIP LOCKED;

-- 2) 逐个原子认领，affected rows = 1 才算成功
UPDATE kb_ingestion_task
SET status = 'RUNNING', locked_by = :instanceId, locked_at = NOW(3), attempt = attempt + 1
WHERE id = :id AND status = 'QUEUED';
```

**规则：认领失败（affected rows = 0）就跳过，不重试认领。**

### 8.3 超时回收

- 调度每 30 秒扫描 `status='RUNNING' AND locked_at < NOW() - INTERVAL 10 MINUTE`。
- 回收动作：置回 `QUEUED`（attempt 已 +1），并写一条 `kb_ingestion_task_log` 说明回收原因。
- 同一文档最多同时存在 1 个非终态任务（由应用层在创建时校验，配合 `T2.7` 测试）。

### 8.4 幂等

- **任务幂等键**：`(doc_id, attempt)`。重试是新 attempt，不是重跑旧记录。
- **分片幂等**：每次执行先 `DELETE FROM kb_document_chunk WHERE doc_id = ?`，再整批写入。
- **向量幂等**：Qdrant point id 由 `hash(doc_id, chunk_seq)` 决定，用 `upsert` 而非 `insert`，重复执行覆盖同一批点。

### 8.5 删除与后台任务的竞态（v1 未覆盖）

处理流程在**三个阶段**校验文档状态，任一阶段发现 `DELETING` 立即中止并丢弃结果：

1. 认领任务时：`JOIN kb_document ON ... WHERE doc.status = 'ACTIVE'`。
2. 写入分片前：重新读一次文档状态。
3. 回写 SUCCESS 前：`UPDATE ... WHERE status = 'ACTIVE'`，affected rows = 0 则丢弃本次结果并触发清理。

**删除流程**：`ACTIVE → DELETING` → 取消该文档所有 QUEUED/RUNNING 任务 → 删文件 → 删分片 → 删向量 → `DELETED`。任一步失败 → `DELETE_FAILED`，进入补偿队列（`@Scheduled` 每 5 分钟重试，最多 5 次）。

### 8.6 失败保留

任务最终失败时保留：`attempt`、`max_attempt`、`error_code`、`error_msg`（截断 2000 字符）、`started_at`、`finished_at`、`locked_by`。前端展示 `error_msg` 与重试按钮；`DEAD` 状态不显示重试按钮，只显示"请联系管理员"。

## 9. 安全设计要点（本轮新增）

### 9.1 服务间认证

- Python 的内部接口路径前缀统一为 `/internal/**`，**不通过 Nginx 暴露到公网**。
- Java → Python 携带 `X-Internal-Token`（`.env` 中的共享密钥，常量时间比较）。缺失或错误一律 401。
- Python 不解析 JWT、不查用户表、不做权限判断。**任何 Python 侧出现 `if user.has_permission` 的代码都是设计错误。**

### 9.2 授权范围由服务端计算

- 客户端只提交 `kbId(s)`，Java 侧用 `AuthzService.readableKbIds(userId)` 计算出实际可读集合，再传给 Python。
- Python 收到的是**已授权的 kbId 列表**，对列表内容不做任何增删。
- 若 Java 传空集合，Python 直接返回空结果，不执行检索。

### 9.3 引用二次鉴权

检索时过滤只是第一道。以下三个动作必须**重新**校验当前用户权限：
1. 打开引用原文（`GET /documents/{id}/chunks/{seq}`）
2. 下载原始文件
3. 从会话里点开历史引用

### 9.4 双启动模式（修正 v1 的一致性矛盾）

| 模式 | 运行在哪 | 命令 | 用途 |
|---|---|---|---|
| **dev** | mysql/redis/qdrant 在容器；Java/Python/Vue 本地进程 | `deploy/scripts/dev.ps1` | 日常开发，热重载 |
| **demo** | 全部在容器 + Nginx | `deploy/scripts/demo.ps1` | 演示与验收 |

**M1 的验收必须用 `demo.ps1`**，否则"docker compose up 后打开登录页"这句话不成立。

### 9.5 SSRF 防护（模型 base_url）

允许用户填写 `base_url` 就要防它被指向内网：

1. 只允许 `https`（本地 Ollama 除外，需显式配置开关）。
2. DNS 解析后校验 IP：拒绝 `10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`（云元数据）、`::1`、`fc00::/7`。
3. 连接测试与真实调用走同一校验函数（不能只校验测试路径）。
4. 文档写明：生产环境应额外做出口网络限制。

### 9.6 密钥管理（修正 v1 的空白）

| 项 | 决定 |
|---|---|
| 主密钥 | `APP_MASTER_KEY`，32 字节 base64，放 `.env`，`.gitignore` 排除 |
| 数据密钥 | `AES-GCM(masterKey, randomIV)`，IV 与密文一起存 `api_key_cipher` 字段 |
| 轮换 | 提供 `rotate-key` 脚本：用旧密钥解密 → 新密钥加密 → 更新，支持 dry-run |
| 主密钥丢失 | **无法恢复**，所有模型密钥需重填。此结论写进运维手册，不假装能恢复 |

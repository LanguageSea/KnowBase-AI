# 知库 AI 企业级 AI 应用开发与运行平台
# 项目实施计划书（V1.0）

**项目名称：** 知库 AI（KnowBase AI）  
**项目定位：** 企业级 AI 应用开发、治理与运行平台  
**计划版本：** V1.0  
**实施方式：** 现有项目迭代升级  
**开发模式：** 人工负责架构决策、代码审查和验收，Codex 辅助开发  
**技术路线：** Vue3 + Spring Boot + Python FastAPI + MySQL + Redis + Qdrant + Docker

---

# 一、项目实施总目标

## 1.1 项目目标

本项目不是简单的知识库问答系统，而是以知识库为基础，逐步建设一个具备 AI 应用开发、模型管理、工作流编排、工具调用、任务调度、效果评估、安全治理和运维监控能力的企业级 AI 平台。

最终实现以下能力：

1. 企业可以创建和管理 AI 应用。
2. 企业可以接入多个大模型，并进行统一管理。
3. 企业可以构建 RAG 知识库问答应用。
4. 企业可以通过工作流组合 AI 模型、知识库和工具。
5. 企业可以管理 AI 工具和外部系统集成。
6. 平台可以统一管理异步任务，并保证任务可靠执行。
7. 平台可以统计模型调用量、成本和运行情况。
8. 平台可以对 AI 应用进行测试、评估和版本发布。
9. 平台具备租户隔离、权限控制和安全审计能力。
10. 平台具备日志、监控、告警、部署和故障恢复能力。

## 1.2 实施原则

- 先审计现有代码，再决定如何改造。
- 优先完善已有模块，不随意推翻已有架构。
- Java 负责平台业务、权限、治理和调度。
- Python 负责 AI 推理、RAG、Agent 和模型适配。
- MySQL 负责业务数据，Qdrant 负责向量数据。
- 先完成模块化单体架构，不为了技术复杂度盲目拆微服务。
- 每个阶段都必须有可运行的成果。
- 所有重要功能都必须有测试和验收标准。
- 不允许 Codex 未经确认直接修改数据库结构或删除现有业务代码。

项目分为九个阶段，按照依赖关系逐步推进。

| 阶段 | 名称 | 主要目标 | 预计时间 |

# 三、详细实施计划

# 第一阶段：现有项目审计

**预计时间：3天**

## 3.1 阶段目标

在增加新功能之前，全面了解当前项目已经实现了什么、哪些功能只是页面展示、哪些接口尚未完成、哪些地方存在架构问题。

不能直接让 Codex 开始增加几十张数据表和大量接口。

首先建立项目现状基线。

## 3.2 具体工作

### 第一步：项目结构审计

检查前端、Java 后端、Python AI 服务和部署文件。

需要检查：

- Vue3 项目目录结构。
- Spring Boot 模块结构。
- Controller、Service、Mapper 的分层情况。
- Python FastAPI 路由和业务模块。
- MySQL 当前数据库表。
- Redis 的使用情况。
- Qdrant Collection 和向量数据结构。
- Docker Compose 和 Nginx 配置。

输出一份项目架构图和目录说明。

### 第二步：功能审计

逐一检查已有页面和接口。

重点检查：

- 登录和权限。
- 用户管理。
- 知识库管理。
- 文档上传和解析。
- 文档分块。
- 向量索引。
- RAG 检索。
- AI 对话。
- 引用溯源。
- 模型配置。
- 管理员设置。
- 操作日志。

每个功能标记为：

1. 已完成且测试通过。
2. 已完成但缺少测试。
3. 只有前端页面。
4. 只有后端接口。
5. 尚未开发。
6. 存在缺陷，需要重构。

### 第三步：数据库审计

检查现有 MySQL 表结构。

重点检查：

- 主键和外键。
- 字段类型和长度。
- 唯一索引。
- 普通索引。
- 逻辑删除。
- 创建时间和更新时间。
- 租户字段。
- 数据关联关系。

必须保留已有业务数据。

新增数据库结构时使用 Flyway 迁移脚本，禁止直接覆盖原有初始化脚本。

### 第四步：接口审计

整理所有接口：

| 项目 | 检查内容 |
|---|---|
| 接口路径 | 是否符合统一规范 |
| 请求参数 | 是否有参数校验 |
| 返回格式 | 是否统一 |
| 权限控制 | 是否有服务端权限校验 |
| 异常处理 | 是否有统一异常处理 |
| 日志 | 是否能定位请求 |
| 测试 | 是否有接口测试 |

## 3.3 交付成果

- 项目现状分析报告。
- 项目目录结构说明。
- 数据库 ER 图。
- 接口清单。
- 功能完成度清单。
- 技术债务清单。
- 后续开发任务清单。

## 3.4 验收标准

- 能够完整启动现有项目。
- 能够说明每个模块的实际职责。
- 能够区分已经实现和未实现的功能。
- 已有数据库数据得到保护。
- 明确后续改造顺序。

让项目从能够在本地运行，升级为具备规范开发、测试、部署和问题定位能力的工程项目。

- 统一响应对象。
- 统一异常处理。
- 统一参数校验。
- 统一日志格式。
- 统一分页处理。
- 统一数据库事务处理。

Python 服务：

- 按业务模块划分目录。
- 统一 Pydantic 请求模型。
- 统一异常返回。
- 统一日志格式。
- 统一配置管理。
- 统一模型调用接口。

Vue 前端：

- 统一 API 请求封装。
- 统一登录状态管理。
- 统一权限路由。
- 统一错误提示。
- 统一表单校验。
- 统一组件规范。

### 第二步：数据库迁移管理

引入 Flyway。

实现：

- 数据库版本管理。
- 增量 SQL 迁移。
- 迁移执行记录。
- 测试环境迁移。
- 生产环境迁移。

每次数据库变更都必须有对应迁移文件。

### 第三步：完善容器部署

建立 Docker Compose 部署环境。

至少包含：

- Vue 前端。
- Nginx。
- Java 后端。
- Python AI 服务。
- MySQL。
- Redis。
- Qdrant。

增加：

- 环境变量模板。
- 健康检查。
- 数据持久化卷。
- 容器重启策略。
- 服务依赖配置。
- 日志目录。
- 数据备份脚本。

### 第四步：建立测试体系

Java：

- JUnit 5。
- Mockito。
- Spring Boot Test。

Python：

- Pytest。
- FastAPI TestClient。

前端：

- Vitest。
- 关键页面组件测试。

接口：

- Apifox 或 Postman。

### 第五步：建立 CI 流程

使用 GitHub Actions 或其他 CI 工具。

流程：

1. 提交代码。
2. 安装依赖。
3. 执行代码检查。

5. 构建 Java。
6. 构建 Python 镜像。

- Flyway 迁移脚本。
- Docker Compose。
- 环境变量模板。
- 自动化测试基础。
- CI 配置文件。
- 项目部署手册。

## 4.4 验收标准

- 新环境可以按照文档完成部署。
- Java 和 Python 服务能够独立启动。
- 数据库迁移可以重复验证。

# 第三阶段：企业组织与权限体系

**预计时间：1.5周**

## 5.1 阶段目标

让系统从单一管理员使用模式，升级为支持多个企业、多个团队和不同角色的企业级平台。

这是后续所有业务模块的基础。

## 5.2 具体工作

### 第一步：租户管理

新增租户管理能力。

租户表示一个独立企业或组织。

实现：

- 租户创建。
- 租户编辑。
- 租户启用和停用。
- 租户管理员分配。
- 租户基本信息管理。

数据库建议：

- tenant。
- tenant_config。

### 第二步：组织和团队管理

支持企业内部组织结构。

例如：

企业 A
- 技术部
  - 后端开发组
  - AI 应用组
- 产品部
- 运维部

实现：

- 部门创建。
- 部门修改。
- 部门删除。
- 部门层级。
- 用户部门分配。
- 团队管理。

### 第三步：角色权限管理

采用 RBAC 权限模型。

角色示例：

| 角色 | 权限 |
|---|---|
| 平台管理员 | 平台级管理 |
| 企业管理员 | 企业内部管理 |
| 普通成员 | 使用授权应用 |
| 应用管理员 | 管理指定 AI 应用 |
| 审计人员 | 查看审计记录 |

实现：

- 角色管理。
- 权限管理。
- 用户角色绑定。
- 菜单权限。
- 接口权限。
- 数据权限。

### 第四步：资源级权限

不能只限制菜单和接口。

还需要控制用户能否访问具体资源。

例如：

- 是否可以访问某个知识库。
- 是否可以查看某个 AI 应用。
- 是否可以修改某个模型配置。
- 是否可以执行某个工作流。
- 是否可以调用某个工具。

所有资源权限必须由后端验证，不能仅依赖前端隐藏按钮。

### 第五步：租户数据隔离

实现租户维度的数据隔离。

重点检查：

- MySQL 查询是否限制 tenant_id。
- Redis Key 是否包含租户隔离信息。
- Qdrant 检索是否携带租户和资源权限过滤条件。
- 文件访问是否验证所属租户。
- AI 服务是否能够识别调用者的权限上下文。

## 5.3 交付成果

- 租户管理页面。
- 组织管理页面。
- 用户角色管理页面。
- 资源权限控制。
- 租户数据隔离机制。
- 权限设计文档。

## 5.4 验收标准

创建两个测试租户：

- 企业 A。
- 企业 B。

分别创建用户、知识库和 AI 应用。

验证：

- A 用户无法访问 B 的数据。
- A 用户不能修改 B 的资源。
- 未授权用户不能调用受保护接口。
- 即使直接构造 HTTP 请求也无法绕过权限控制。

# 第四阶段：AI 模型治理中心

**预计时间：1.5周**

## 6.1 阶段目标

将原有的单一模型配置功能升级为统一的 AI 模型接入和治理中心。

平台可以同时连接多个大模型服务商，并根据业务策略进行模型选择。

## 6.2 具体工作

### 第一步：模型供应商管理

支持添加不同模型供应商。

例如：

- OpenAI 兼容接口。
- DeepSeek。
- 通义千问。
- 智谱。
- Ollama。
- 其他兼容服务。

实现：

- 供应商名称。
- API 地址。
- API Key。
- 连接测试。
- 启用和禁用。
- 模型列表。

API Key 必须加密保存，不能明文返回前端。

### 第二步：模型统一适配

Python AI 服务建立统一模型调用接口。

统一处理：

- Chat。
- Embedding。
- Rerank。
- 流式输出。
- 非流式输出。
- Token 使用量。
- 超时。
- 异常。

不同供应商通过适配器实现。

### 第三步：模型路由

实现模型路由规则。

例如：

| 业务类型 | 模型策略 |
|---|---|
| 普通问答 | 低成本模型 |
| 复杂推理 | 高能力模型 |
| 文本向量化 | Embedding 模型 |
| 文档重排 | Rerank 模型 |

第一版先支持规则路由，不必立即实现复杂的机器学习路由。

### 第四步：模型故障切换

例如：

主模型调用失败：

1. 判断是否属于可重试错误。
2. 执行有限次数重试。
3. 检查备用模型是否可用。
4. 切换到备用模型。
5. 记录故障和切换原因。

注意：非幂等调用不能盲目重试，必须控制重复调用和费用。

### 第五步：调用统计和成本管理

记录：

- 请求用户。
- 所属租户。
- 所属应用。
- 使用模型。
- 输入 Token。
- 输出 Token。
- 调用耗时。
- 调用状态。
- 错误原因。
- 估算费用。

建立模型使用统计页面。

成本数据应明确标记为估算值，除非已经获得供应商账单数据。

### 第六步：配额管理

支持：

- 租户日调用额度。
- 用户日调用额度。
- 应用调用额度。
- Token 限额。
- 费用预算。
- 超额告警。

## 6.3 交付成果

- 模型供应商管理。
- 模型列表。
- 模型统一适配层。
- 模型路由。
- 故障切换。
- Token 统计。
- 成本统计。
- 配额管理。

## 6.4 验收标准

- 至少接入两个不同模型服务。
- 能够测试模型连通性。
- 能够根据路由规则选择模型。
- 主模型故障时可以切换备用模型。
- 可以查询用户、租户和应用的模型使用量。
- API Key 不会通过接口或日志泄漏。

# 第五阶段：AI 应用管理中心

让用户不仅能够使用平台提供的知识库，还能够自主创建、配置、测试和发布 AI 应用。

知识库问答只是其中一种应用类型。

## 7.2 具体工作

### 第一步：AI 应用类型设计

第一版支持：

1. RAG 知识库问答。
2. AI 智能助手。
3. 文本总结。
4. 文本分类。
5. 信息提取。

后续可以增加 Agent 和多模态应用。

用户填写：

- 应用名称。
- 应用描述。
- 应用类型。
- 应用图标。
- 系统提示词。
- 默认模型。
- 关联知识库。
- 应用访问权限。

### 第三步：应用配置

不同应用具有不同配置。

RAG 应用：

- Top K。
- 相似度阈值。
- Chunk 策略。
- 是否启用 Rerank。
- 是否显示引用。

文本总结：

- 提示词模板。
- 输出长度。
- 输出格式。
- 使用模型。

### 第四步：应用测试

提供测试对话窗口。

支持：

- 输入测试内容。
- 查看模型响应。
- 查看 Token 消耗。
- 查看调用耗时。
- 查看引用来源。

### 第五步：版本管理

建立应用版本机制。

例如：

- V1：基础 RAG。
- V2：增加 Rerank。
- V3：调整提示词。

实现：

- 版本创建。
- 版本配置快照。
- 版本发布。
- 版本回滚。
- 发布记录。

已经发布的版本不能因为编辑草稿而被静默修改。

## 7.3 交付成果

- AI 应用列表。
- 应用创建页面。
- 应用配置页面。
- 应用测试页面。
- 应用版本管理。
- 应用发布和回滚。

## 7.4 验收标准

- 用户可以创建不同类型的 AI 应用。
- 应用可以关联模型和知识库。
- 修改草稿不会影响线上版本。
- 可以发布指定版本。
- 可以回滚历史版本。
- 普通用户只能访问授权应用。

# 第六阶段：工作流与工具平台

**预计时间：2周**

## 8.1 阶段目标

实现平台最重要的差异化功能之一：让用户能够将模型、知识库和工具组合成自动化 AI 工作流。

## 8.2 具体工作

### 第一步：工作流设计

第一版采用 DAG 有向无环图执行模式。

先支持以下节点：

| 节点 | 作用 |
|---|---|
| 开始节点 | 接收用户输入 |
| 结束节点 | 返回最终结果 |
| LLM 节点 | 调用大模型 |
| 知识检索节点 | 从知识库获取内容 |
| HTTP 节点 | 调用外部 API |
| 条件节点 | 根据条件分支 |
| 代码节点 | 执行受限的业务逻辑 |
| 人工审核节点 | 等待人工确认 |

### 第二步：工作流画布

前端使用 Vue3 配合 Vue Flow。

实现：

- 节点拖拽。
- 节点连接。
- 节点配置。
- 节点删除。
- 工作流保存。
- 工作流加载。
- 节点参数校验。

### 第三步：工作流 DSL

前端画布不能直接负责真正的业务执行。

需要将画布转换成统一 DSL。

例如：

```json
{
  "nodes": [
    {
      "id": "start",
      "type": "start"
    },
    {
      "id": "llm",
      "type": "llm",
      "config": {
        "model": "default",
        "prompt": "分析用户问题"
      }
    },
    {
      "id": "end",
      "type": "end"
    }
  ],
  "edges": [
    {
      "source": "start",
      "target": "llm"
    },
    {
      "source": "llm",
      "target": "end"
    }
  ]
}
```

执行前需要校验：

- 节点是否存在。
- 连线是否合法。
- 是否存在无法到达的节点。
- 参数是否完整。
- 是否存在非法循环。
- 工作流是否超过执行限制。

### 第四步：工作流执行引擎

Python 负责 AI 节点执行，Java 负责平台侧的工作流管理和权限治理。

具体实现：

1. 接收工作流执行请求。
2. 获取已发布的工作流版本。
3. 校验用户权限。
4. 创建执行记录。
5. 根据 DAG 顺序调度节点。
6. 保存节点执行结果。
7. 处理失败和超时。
8. 返回执行结果。

第一版不需要追求复杂的分布式工作流系统。

### 第五步：工具中心

建立统一工具注册机制。

第一版支持：

- HTTP API 工具。
- 内部 Java 服务工具。
- Python 工具。
- MCP 工具接口（作为后续扩展）。

每个工具需要定义：

- 工具名称。
- 工具描述。
- 输入参数 Schema。
- 输出结果 Schema。
- 调用权限。
- 超时时间。
- 风险等级。
- 工具版本。

### 第六步：人工审批

对高风险操作加入人工审批。

例如：

AI 可以生成删除数据的操作建议，但真正执行前必须经过授权人员确认。

工具执行必须有权限校验、参数校验、审计记录和网络访问限制。

## 8.3 交付成果

- 工作流管理。
- 可视化画布。
- 工作流 DSL。
- DAG 校验器。
- 工作流执行引擎。
- 工具注册中心。
- 工具权限管理。
- 人工审批机制。
- 节点运行记录。

## 8.4 验收标准

用户输入问题 → 知识库检索 → LLM 分析 → 调用 HTTP 工具 → 人工审批 → 返回结果。

同时验证：

# 第七阶段：可靠任务与 AI 效果评估

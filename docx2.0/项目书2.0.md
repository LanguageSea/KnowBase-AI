# 知库 AI（KnowBase AI）
# 企业级 AI 应用开发与运行平台项目书

**项目名称：** 知库 AI（KnowBase AI Platform）  
**项目定位：** 企业级 AI 应用开发、治理、运行与运维平台  
**项目版本：** V2.0 规划版  
**文档类型：** 项目立项书 / 总体建设方案  
**技术路线：** Vue 3 + Spring Boot + FastAPI + MySQL + Redis + Qdrant  
**建设目标：** 从单一知识库问答系统升级为可扩展、可治理、可观测、可持续迭代的企业 AI 应用平台。

---

# 一、项目概述

## 1.1 项目背景

随着大语言模型在企业知识管理、业务自动化、数据分析、客服辅助和内部办公等领域的应用不断深入，企业对 AI 系统的需求已经从简单的模型对话逐步扩展到多模型统一接入、私有数据检索、业务工具调用、自动化流程编排、应用版本管理、安全治理和运行质量评估。

传统 AI 应用通常围绕单一业务场景开发，例如企业知识库问答系统。此类系统能够完成文档上传、向量检索和模型生成，但在应用规模扩大后，往往会遇到以下问题：

1. 不同 AI 应用重复开发模型调用、权限控制和日志记录逻辑。
2. 多个模型供应商接口不统一，模型切换和故障降级困难。
3. AI 应用缺乏完整的版本管理、测试验证和发布回滚机制。
4. 多步骤 AI 任务难以可靠执行，进程重启后容易丢失运行状态。
5. AI 调用成本、工具权限和数据访问缺少统一治理。
6. 缺少可复现的评测体系，难以客观判断模型、提示词和检索策略是否真正改善。
7. 系统上线后缺乏完整的链路追踪、故障告警和恢复机制。

因此，本项目计划在现有知库 AI 知识库问答系统的基础上，建设一套企业级 AI 应用开发与运行平台，为不同业务场景提供统一的模型能力、知识检索、工具调用、工作流编排、安全治理和运维能力。

## 1.2 项目定位

知库 AI 不再局限于一个知识库问答产品，而是定位为企业 AI 应用的统一运行与治理平台。

平台采用“平台核心 + AI 运行时 + 可复用能力模块”的设计思路：

- **平台核心：** 负责用户、组织、权限、应用、版本、配额、审计和业务管理。
- **AI 运行时：** 负责模型调用、RAG、结构化抽取、AI 评测和受控智能体执行。
- **自动化能力：** 负责工作流、任务调度、工具调用、审批和失败恢复。
- **治理与运维：** 负责安全策略、质量门禁、日志追踪、告警和发布管理。

知识库仍然是平台的重要业务模块，但平台未来可以承载多种 AI 应用，而不必为每种应用重新建设一套后台系统。

## 1.3 项目建设目标

本项目需要实现以下目标：

1. 建立统一的企业 AI 应用管理和运行体系。
2. 支持多个模型端点的统一接入、路由、限流和故障处理。
3. 支持 AI 应用版本管理、测试、发布和回滚。
4. 支持可视化工作流和持久化任务执行。
5. 支持可授权、可审计、可限制的外部工具调用。
6. 建立 AI 应用质量评测和发布质量门禁。
7. 实现跨 Java、Python、数据库及模型服务的可观测性。
8. 建立生产环境所需的安全控制、备份恢复、自动化测试和发布流程。
9. 保持现有项目架构的连续性，采用增量升级方式完成建设。
10. 最终形成可部署、可演示、可测试并能够持续迭代的完整项目。

# 二、项目现状与建设原则

## 2.1 现有技术基础

项目现有技术架构为：

| 技术 | 当前定位 |
|---|---|
| Vue 3 | 前端管理界面、知识库页面、交互功能 |
| Spring Boot | 业务 API、用户管理、权限控制、业务数据管理 |
| FastAPI | Python AI 服务、模型调用、RAG 相关处理 |
| MySQL | 业务数据、配置、任务及审计记录 |
| Redis | 缓存、临时状态、并发控制等适用场景 |
| Qdrant | 向量数据存储与相似度检索 |
| Docker Compose | 开发和部署阶段的容器化编排 |
| 大模型 API | 提供文本生成、Embedding 等模型能力 |

现有系统已经包含或规划了登录、知识库管理、文档处理、问答、引用来源、模型配置、审计及基础部署等功能。

实际建设时，必须以当前代码、数据库迁移脚本和测试结果为准，不能仅凭功能规划认定某项功能已经完成。

## 2.2 建设原则

### 原则一：增量升级，不推倒重建

保留现有 Vue 3、Spring Boot、FastAPI、MySQL、Redis 和 Qdrant 技术路线。优先复用现有用户、知识库、文档、模型、任务和审计模块。

### 原则二：模块化单体优先

Java 平台核心采用模块化单体架构，Python AI Runtime 作为独立服务部署。只有在出现明确的独立扩缩容、故障隔离或团队协作需求时，才考虑继续拆分服务。

### 原则三：可靠性优先于功能数量

所有长任务、工作流、工具调用和外部 API 请求都必须定义超时、失败处理、幂等和恢复策略。

### 原则四：安全贯穿全链路

权限控制不能仅停留在页面和普通接口，还必须覆盖缓存、后台任务、文件访问、向量检索、模型调用和工具执行。

### 原则五：AI 效果必须可评估

平台需要通过固定数据集、评测指标和版本记录比较模型与应用效果，避免仅凭主观感受判断质量。

### 原则六：上线能力必须可验证

部署成功不等于系统可上线。必须完成安全检查、自动化测试、备份恢复演练、故障演练和运行指标验证。

# 三、用户角色与业务场景

## 3.1 用户角色

### 平台管理员

负责平台级配置、租户管理、模型端点、配额策略、安全策略和运维配置。

### 企业管理员

负责本企业的成员、团队、知识资源、应用授权和使用情况管理。

### AI 应用开发者

负责创建 AI 应用、编排工作流、绑定模型和工具、维护应用版本、执行测试和提交发布。

### 普通业务用户

负责使用已授权的 AI 应用、查询知识、执行允许的自动化流程和查看个人任务。

### 运维人员

负责监控服务健康状态、查看告警、分析调用链路、处理任务故障和执行授权范围内的运维操作。

## 3.2 典型业务场景

**场景一：企业知识问答**

用户提出问题，平台验证权限，检索授权知识，调用模型生成回答，并返回引用来源和执行记录。

**场景二：企业文档处理**

平台接收文档，执行解析、结构化抽取和分类，将结果保存为可追踪的数据资产。

**场景三：AI 业务自动化**

工作流读取授权数据，调用 AI 分析，生成结果后进入人工审批，审批通过后调用外部系统执行操作。

**场景四：模型质量比较**

开发者使用固定评测集比较不同模型、提示词或检索配置，生成评测报告，并依据质量门禁决定是否发布。

**场景五：生产故障处理**

模型接口发生超时，平台记录调用链路、触发告警、执行备用路由或失败策略，并允许运维人员定位和恢复受影响任务。

# 四、总体系统架构

## 4.1 架构设计

系统采用分层架构，并明确各层之间的职责边界。

```text
┌──────────────────────────────────────────┐
│                Vue 3 前端                │
│ 管理控制台 / AI 应用 / 工作流画布 / 运维  │
└──────────────────┬───────────────────────┘
                   │ HTTPS / SSE
┌──────────────────▼───────────────────────┐
│             Spring Boot 平台核心          │
│ 身份权限 / 租户组织 / 应用版本 / 配额治理 │
│ 模型网关 / 任务协调 / 工具管理 / 审计     │
└──────────────┬────────────────┬──────────┘
               │                │
┌──────────────▼─────────┐ ┌────▼─────────────┐
│   Python AI Runtime    │ │ 工作流与任务执行  │
│ RAG / 模型适配 / 评测   │ │ 状态机 / 重试恢复 │
│ 抽取 / 工具执行适配     │ │ 审批 / 幂等 / 补偿 │
└──────────────┬─────────┘ └────┬─────────────┘
               │                │
┌──────────────▼────────────────▼─────────────┐
│                   数据层                    │
│ MySQL / Redis / Qdrant / 对象存储            │
└─────────────────────────────────────────────┘

外部依赖：
模型供应商 / 企业业务 API / 监控与日志系统 / 密钥管理服务
```

## 4.2 Java 平台核心职责

Spring Boot 负责稳定、可审计的企业业务逻辑，包括：

- 用户、租户、组织和资源权限。
- AI 应用管理、版本、发布和授权。
- 模型端点、路由、预算和调用记录。
- 工具定义、连接器配置和审批管理。
- 任务、工作流状态和执行协调。
- 安全策略、审计日志和运维管理 API。

## 4.3 Python AI Runtime 职责

FastAPI 负责适合 Python 生态的 AI 能力：

- 模型供应商适配。
- RAG 检索和生成。
- 文本分类、结构化抽取和内容处理。
- AI 评测执行。
- 受控 Agent 的模型推理与步骤执行。
- Python 侧健康检查、运行指标和异常处理。

Python 服务不能绕过 Java 的权限治理，直接获得所有企业数据或工具凭据。

## 4.4 数据存储职责

- MySQL：业务数据、权限、应用版本、任务状态、审计和评测元数据。
- Redis：适合的热点缓存、限流计数、短期状态和并发协调。
- Qdrant：向量索引与相似度检索。
- 对象存储：原始文档、导出文件和较大的解析产物。
- 可观测性系统：Trace、指标、日志和告警数据。

重要业务状态不能只保存在 Redis 或进程内存中。缓存失效、进程重启和任务恢复都必须有明确设计。

# 五、功能模块设计

## 5.1 模块一：企业组织、身份与资源权限

**建设级别：P0，必须做**

### 功能范围

1. 租户、组织、团队管理。
2. 用户与组织关系管理。
3. 角色和权限管理。
4. 资源级授权。
5. 用户离职、权限撤销和访问失效处理。
6. 权限变更审计。
7. 资源访问模拟和越权测试。

### 技术方案

基于 Spring Security 统一认证与授权，在现有角色体系上扩展资源权限和租户上下文。

所有关键资源都必须验证归属，包括知识库、文档、AI 应用、工作流、工具、任务和评测数据。

### 预期成果

形成统一的权限基础，为模型治理、工具调用和企业数据集成提供安全边界。

---

## 5.2 模块二：模型网关与模型治理

**建设级别：P1，推荐做**

### 功能范围

1. 多模型供应商统一接入。
2. 模型能力注册和分类。
3. 模型路由策略。
4. 备用模型与故障降级。
5. 调用超时、并发限制和有限重试。
6. Token 使用统计。
7. 成本估算与预算告警。
8. 模型调用记录与审计。
9. 模型端点健康状态监测。

### 技术方案

建立统一模型适配器，对外提供标准调用接口，对内保留供应商差异。

模型路由根据应用配置、任务类型、模型能力、成本和可用性选择端点。流式请求需要处理上游中断、客户端取消和资源释放。

成本记录区分供应商实际报告的用量、根据价格配置估算的费用，以及供应商账单数据。

### 预期成果

平台应用不再直接绑定某个模型供应商，模型切换和故障处理可以集中管理。

---

## 5.3 模块三：AI 应用管理与版本发布

**建设级别：P1，推荐做**

### 功能范围

1. AI 应用注册与分类。
2. 应用参数和输入输出 Schema。
3. 模型、知识源和工具绑定。
4. 应用版本管理。
5. 草稿、测试、待审批、正式发布和停用。
6. 发布历史和配置差异。
7. 灰度发布与回滚。
8. 应用使用统计。

### 技术方案

将应用定义、版本和运行实例分开管理。

每个发布版本保存可追溯配置快照。运行中的任务使用启动时确定的版本，避免后台配置更新导致执行行为不可预测。

### 预期成果

实现可维护、可测试、可发布、可回滚的 AI 应用生命周期。

---

## 5.4 模块四：可视化工作流平台

**建设级别：P1，推荐做**

### 功能范围

1. 工作流画布。
2. 节点拖拽、连线和配置。
3. 输入输出 Schema。
4. 条件分支。
5. AI 调用节点。
6. 工具调用节点。
7. 人工审批节点。
8. 执行历史和节点级错误记录。
9. 重试、暂停和恢复。
10. 工作流版本管理。

### 技术方案

采用受限 DAG 作为第一版执行模型，使用 JSON 描述流程结构。

Java 负责工作流管理、权限、持久化状态和业务协调；Python 提供 AI 执行能力。

工作流状态和节点状态需要持久化，避免依赖内存中的执行上下文。外部写操作必须具有幂等机制，必要时定义补偿动作。

### 典型流程

```text
开始
  ↓
读取授权业务数据
  ↓
AI 分析与结构化抽取
  ↓
条件判断
  ├── 低风险 → 生成报告
  └── 高风险 → 人工审批
                   ↓
               执行授权操作
                   ↓
               记录执行结果
```

### 预期成果

使平台从单次 AI 请求扩展到多步骤业务自动化。

---

## 5.5 模块五：工具中心与外部系统集成

**建设级别：P1，推荐做**

### 功能范围

1. 工具注册和分类。
2. 输入输出 Schema。
3. 工具版本管理。
4. REST API 和 MCP 接入。
5. 凭据绑定。
6. 调用权限和风险等级。
7. 超时、限流和失败处理。
8. 高风险操作审批。
9. 调用记录和审计。

### 技术方案

工具执行前验证调用主体、应用授权和参数。

所有外部网络访问必须配置目标地址限制、网络出口控制和响应大小限制，防止 SSRF 等安全问题。

高风险写操作默认要求明确授权或人工审批。工具返回内容应作为不可信数据处理，不允许其内容直接修改平台安全策略。

### 预期成果

形成可复用的工具集成能力，使不同 AI 应用可以在统一安全边界内访问业务系统。

---

## 5.6 模块六：可靠任务中心

**建设级别：P0，必须做**

### 功能范围

1. 统一任务查询。
2. 任务状态管理。
3. 超时和取消。
4. 重试与退避。
5. 执行尝试记录。
6. 心跳和租约。
7. 失败任务恢复。
8. 幂等控制。
9. 任务优先级。
10. 执行耗时和失败原因统计。

### 技术方案

先在现有任务机制上实现持久化状态机、条件领取、租约回收和幂等控制。

初期可以保留数据库任务表与调度机制；当吞吐量、并发或解耦需求明确后，再引入 RabbitMQ 等消息基础设施。

任务状态更新与事件发布需要考虑数据库事务和消息发送的一致性，必要时采用 Transactional Outbox 模式。

### 预期成果

提高文档处理、同步、评测和工作流任务的可靠性。

---

## 5.7 模块七：AI 评测与实验平台

**建设级别：P1，推荐做**

### 功能范围

1. 评测数据集管理。
2. 测试用例版本管理。
3. 模型与提示词对比。
4. 检索策略对比。
5. 批量评测。
6. 失败样本查看。
7. 人工复核。
8. 质量门禁。
9. 评测报告导出。

### 技术方案

不同应用采用不同评测指标：

- RAG：Recall@K、MRR、nDCG、引用证据支持度。
- 分类：Precision、Recall、F1。
- 结构化抽取：Schema 合法率、字段准确率。
- 工具调用：任务完成率、参数正确率、越权拦截率。
- 平台性能：延迟、失败率、用量和估算成本。

### 预期成果

建立可复现的 AI 质量验证体系，为应用版本发布提供依据。

---

## 5.8 模块八：数据连接器与数据治理

**建设级别：P1，推荐做**

### 功能范围

1. REST API 数据源。
2. 受控只读数据库视图。
3. 对象存储数据源。
4. 定时同步和增量同步。
5. 同步检查点。
6. 数据质量检查。
7. 数据血缘。
8. 删除和权限变更传播。
9. 数据源健康检查。

### 技术方案

建立统一连接器接口，为不同数据源提供标准的读取、转换、同步和错误处理流程。

同步过程使用任务中心管理，增量同步保存检查点，数据处理结果进入现有文档解析和索引流程。

### 预期成果

从手动上传文档扩展到可持续更新的企业数据接入平台。

## 5.9 模块九：安全策略与 AI 治理

**建设级别：P0 基础安全必须做，P1 高级策略推荐做**

### 功能范围

1. 敏感数据检测与脱敏。
2. 模型使用策略。
3. 工具调用策略。
4. 高风险操作审批。
5. 凭据访问审计。
6. 数据保留和删除策略。
7. 提示注入风险测试。
8. 安全事件记录。
9. 权限变更影响模拟。

### 技术方案

建立统一策略评估接口，根据调用主体、资源、数据分类、目标模型、工具操作和风险等级输出允许、拒绝、脱敏或需要审批的决策。

不能仅依赖提示词或模型自身判断实现安全隔离。真正的安全边界必须由服务端授权、数据过滤、网络限制、执行沙箱和人工审批共同建立。

### 预期成果

形成覆盖数据访问、模型调用和工具执行的安全治理机制。

## 5.10 模块十：可观测性与生产运维

### 功能范围

1. 全链路 Trace。
2. 结构化日志。
3. 服务健康检查。
4. 业务指标采集。
5. 任务积压监控。
6. 模型调用监控。
7. 告警规则与告警事件。
8. 事故记录。
9. 故障演练。
10. 备份恢复记录。

### 技术方案

使用 OpenTelemetry 生态打通 Java、Python 和外部调用链路，使用 Prometheus、Grafana 等工具展示指标，日志和 Trace 存入适合的后端系统。

通过统一 Trace ID 关联请求、任务、工作流节点和模型调用。敏感信息必须在采集前或采集过程中脱敏。

### 预期成果

建立能够定位问题、发现异常、跟踪恢复过程的生产运维体系。

# 六、数据库设计总体规划

## 6.1 设计目标

数据库扩展采用增量方式，优先复用已有业务表，避免一次性创建大量暂时没有业务需求的表。

## 6.2 规划中的核心实体

| 领域 | 主要实体 |
|---|---|
| 身份与组织 | tenant、organization、team、user_tenant_membership |
| 授权治理 | role_binding、resource_policy、authorization_audit |
| 模型治理 | model_capability、model_route_policy、model_call_record |
| 配额与用量 | quota_policy、usage_reservation、usage_ledger |
| AI 应用 | ai_application、application_version、application_release |
| 工作流 | workflow_definition、workflow_version、workflow_execution、node_execution |
| 工具中心 | tool_definition、tool_version、tool_permission、tool_execution |
| 任务中心 | task_attempt、task_event、task_deduplication |
| 数据连接器 | data_source、sync_job、sync_checkpoint、data_lineage |
| AI 评测 | evaluation_dataset、evaluation_case、evaluation_run、evaluation_result |
| 安全策略 | security_policy、policy_revision、policy_decision_audit |
| 运维治理 | alert_rule、alert_event、incident_record、ops_action_audit |

上述名称是逻辑规划，不代表当前数据库中不存在同名或相似实体。实际建表之前必须核对现有 Schema。

## 6.3 数据设计规范

1. 所有核心表明确主键、唯一约束、外键策略和必要索引。
2. 所有关键运行记录具有创建时间、更新时间和状态字段。
3. 对并发更新采用版本号、乐观锁或条件更新。
4. 对幂等请求建立可靠的唯一性约束。
5. 大文本、原始文件和日志不应无差别地塞入业务主表。
6. 删除业务数据时明确关联向量、缓存、文件、引用和备份的处理方式。
7. 使用版本化迁移脚本管理 Schema 变化。
8. 对审计数据建立访问权限、保留期限和完整性保护。

# 七、核心 API 设计规范

## 7.1 API 设计原则

- 统一使用 `/api/v1` 作为公开业务 API 前缀。
- 使用 DTO 接收请求，避免直接暴露数据库实体。
- 对请求参数、输入长度、文件大小和数据格式进行校验。
- 使用统一错误码、错误信息和 Trace ID。
- 对列表接口提供分页、过滤和排序。
- 对长任务返回任务 ID，提供状态查询。
- 对流式接口明确取消、断开和错误语义。
- 对高风险操作要求授权、审计和必要的二次确认。

## 7.2 示例接口

| 领域 | 示例接口 | 用途 |
|---|---|---|
| 应用管理 | `POST /api/v1/applications` | 创建 AI 应用 |
| 应用发布 | `POST /api/v1/applications/{id}/publish` | 发布应用版本 |
| 模型治理 | `POST /api/v1/model-routes` | 创建模型路由策略 |
| 任务管理 | `GET /api/v1/tasks/{id}` | 查询任务状态 |
| 工作流 | `POST /api/v1/workflows/{id}/execute` | 启动工作流 |
| 工具管理 | `POST /api/v1/tools/{id}/test` | 测试工具连接 |
| AI 评测 | `POST /api/v1/evaluation-runs` | 创建评测任务 |
| 数据连接器 | `POST /api/v1/data-sources/{id}/sync` | 启动数据同步 |
| 安全治理 | `POST /api/v1/security/policies/{id}/simulate` | 模拟策略执行 |
| 运维管理 | `GET /api/v1/ops/traces/{traceId}` | 查询调用链路 |

实际接口应以现有 API 命名、认证机制和版本规范为基础进行统一，不应机械复制以上路径。

# 八、非功能性需求

## 8.1 安全要求

- 所有生产通信使用 HTTPS。
- 所有业务资源执行服务端权限检查。
- 密钥与普通业务配置分离。
- 限制上传文件大小、格式和解析资源。
- 对外部网络访问设置允许范围。
- 对高风险工具操作实施审批或显式确认。
- 日志、Trace 和导出数据执行敏感信息保护。
- 建立依赖漏洞扫描、权限测试和安全回归测试。

## 8.2 性能要求

性能指标需要在部署环境、硬件规格、数据规模和模型端点确定后制定。

上线前至少完成以下基准测试：

- 普通业务 API 的延迟与吞吐量。
- 多用户并发访问。
- 文档解析和索引吞吐量。
- Qdrant 检索延迟。
- 模型调用成功率和响应时间。
- 长任务积压和恢复能力。
- 数据库慢查询和连接池使用情况。

所有性能报告必须注明测试环境、数据规模、并发量和统计方法，不得用未经测试的数值作为项目成果。

## 8.3 可用性与恢复要求

- 关键服务提供健康检查。
- 长任务支持恢复和有限重试。
- 数据库与重要文件具有备份方案。
- 备份必须定期验证可恢复性。
- 关键依赖发生故障时，平台能够明确报错、降级或暂停任务。
- 明确恢复时间目标（RTO）和允许数据丢失范围（RPO），并通过演练验证。

## 8.4 可维护性要求

- 业务模块具有清晰的代码边界。
- API、数据库和配置变更有版本记录。
- 核心业务具备自动化测试。
- 生产配置与开发配置分离。
- 日志能够关联请求和任务。
- 部署、升级、回滚和故障处理具有文档。

# 十一、测试与验收方案

## 11.1 功能验收

- 用户能够创建并运行 AI 应用。
- 不同模型端点能够通过统一接口调用。
- 应用版本能够发布、查看和回滚。
- 工作流能够执行 AI、工具和审批节点。
- 任务失败后能够按策略重试或恢复。
- 评测任务能够生成可追溯的结果。
- 管理员能够查看应用使用情况和运行记录。

## 11.2 权限与安全验收

- 跨租户资源访问被拒绝。
- 被撤销的权限不会继续授权新的任务执行。
- 未授权工具调用无法执行。
- 敏感凭据不会出现在前端和普通日志中。
- 外部连接器不能访问未允许的目标地址。
- 上传与解析功能对恶意输入和资源耗尽进行限制。

## 11.3 可靠性验收

- 模型超时能够触发预期的错误或降级策略。
- Worker 中断后任务能够按规则恢复。
- 重复请求不会导致重复业务副作用。
- Redis、Qdrant 或外部模型暂时不可用时，系统能够给出明确状态。
- 数据库备份能够恢复到经过验证的状态。
- 应用升级失败时有可执行的恢复方案。

## 11.4 可观测性验收

- 可以通过 Trace ID 定位一次完整请求。
- 可以查询任务执行历史和失败原因。
- 能够检测任务积压、模型错误率和服务健康异常。
- 重要安全操作具有审计记录。
- 关键故障有告警、处置和恢复记录。

## 11.5 交付验收

- 代码能够在规定环境中构建。
- 数据库迁移可以按顺序执行。
- 自动化测试结果可重复验证。
- 部署文档、环境变量模板和故障排查手册齐全。
- 项目演示使用可控测试数据，不泄露真实企业数据或生产密钥。
- 项目介绍中的功能、性能和安全结论均有实际证据支持。

# 十二、项目风险与应对措施

## 12.1 项目范围膨胀

风险：功能数量过多，导致核心闭环始终无法完成。

应对：采用 P0、P1、P2 分级，每个阶段只推进有限数量的可验收模块；未完成的功能不提前宣称上线。

## 12.2 AI 输出不稳定

风险：相同输入可能产生不同结果，模型升级后质量发生变化。

应对：固定评测集、记录模型和提示词版本、建立质量门禁，对高风险操作增加规则校验和人工审批。

## 12.3 任务重复执行

风险：网络中断、消息重投或 Worker 崩溃可能导致重复副作用。

应对：幂等键、唯一约束、任务尝试记录、状态机和补偿机制协同设计。

## 12.4 权限边界不完整

风险：接口权限正确，但缓存、向量检索、异步任务或工具调用出现越权。

应对：统一授权服务，在每个数据访问和执行边界验证权限，并通过跨租户自动化测试持续检查。

## 12.5 基础设施过度复杂

风险：过早引入大量分布式组件，增加开发和运维成本。

应对：保持模块化单体和独立 AI Runtime；只有在有真实业务依据时才引入消息队列、分布式工作流引擎或容器编排。

## 12.6 线上数据和密钥泄漏

风险：日志、错误堆栈、提示词或配置导出包含敏感信息。

应对：密钥分离、字段脱敏、权限审计、最小权限、备份保护和生产安全测试。

# 十五、最终建设结论

知库 AI 的升级目标不是简单增加更多页面，而是从知识库问答应用逐步演进为一套具备统一模型治理、应用生命周期管理、工作流执行、工具集成、AI 质量评测、安全治理和生产运维能力的企业级 AI 平台。

项目坚持以下建设路径：
